# Wallpaper API v1 contract

Status: frozen for `WAPI-02`.

This document defines the boundary between `download-bing-wallpaper` v3, the
wallpaper ingestion service, and public API clients. It is intentionally
independent of Laravel and PHP so that another service or frontend can consume
the same contract.

## Composer command input

The API invokes the package as a bounded child process:

```text
php artisan bing:wallpaper --date=YYYY-MM-DD --no-ansi --no-interaction
```

The requested date is a real proleptic Gregorian calendar date in the canonical
four-digit-year format `YYYY-MM-DD`. There is no product-level minimum, maximum,
or range substitution. An accepted date is not a promise that Bing can return a
wallpaper for that date.

The command writes exactly one UTF-8 JSON document followed by one newline to
standard output. Defined results leave standard error empty.

## Composer document compatibility

`schemaVersion` is a string in `major.minor` form.

- Consumers accept major version `1`, including later `1.x` documents.
- A minor release may only add optional fields. Consumers ignore unknown fields.
- Every required v1 field keeps its documented type and meaning throughout the
  major version.
- Consumers reject a missing, malformed, or unsupported major version before
  persistence.
- Consumers validate the complete envelope and the exit-code/status pairing.
  Malformed JSON, multiple JSON documents, missing fields, invalid field types,
  inconsistent values, or an unknown status make the ingestion attempt fail.

The required envelope fields are:

| Field | Type | Meaning |
| --- | --- | --- |
| `schemaVersion` | string | Producer contract version. |
| `status` | `found`, `not_found`, or `error` | Result category. |
| `query` | object | Exact source query issued by the package. |
| `data` | object or null | Normalized wallpaper metadata. |
| `rawPayload` | any JSON value | Unmodified decoded upstream payload when available. |
| `error` | object or null | Stable technical error information. |
| `retrievedAt` | string | UTC timestamp in `YYYY-MM-DDTHH:MM:SSZ` form. |

`query` requires `source`, `market`, and `date`. For v1, `source` is `bing`,
`market` is `en-US`, and a request made by the API must echo the requested date.

### `found`

`found` requires exit code `0`, `error: null`, and a non-null `data` object:

| Field | Type |
| --- | --- |
| `sourceDate` | `YYYY-MM-DD` string |
| `sourceItemId` | non-empty string |
| `title` | string or null |
| `copyright` | string or null |
| `copyrightLink` | absolute HTTPS URL or null |
| `imageUrl` | absolute HTTPS URL |
| `downloadUrl` | absolute HTTPS URL or null |

Both `query.date` and `data.sourceDate` must equal the requested date. A
consumer rejects a document that returns a substituted date.

### `not_found`

`not_found` requires exit code `0`, `data: null`, and `error: null`. It is a
successful lookup with no exact match, not a technical failure. The API records
the synchronization attempt but does not create a wallpaper record.

### `error`

`error` requires exit code `1` for upstream or internal failures, or exit code
`2` for invalid command input. `data` is null and `error` contains:

| Field | Type | Meaning |
| --- | --- | --- |
| `code` | non-empty string | Stable machine-readable code. |
| `message` | non-empty string | Sanitized diagnostic message. |
| `retryable` | boolean | Whether a later operator-initiated attempt may succeed. |

The API records the failed synchronization and does not write partial wallpaper
data. Version 1 does not retry automatically. `rawPayload`, command diagnostics,
and the internal error object are never returned by the public API.

Consumers preserve JSON value types inside `rawPayload`, including the
difference between an empty object (`{}`) and an empty array (`[]`). They may
store the entire value as JSON, but must not infer normalized fields from it.

## Public query endpoint

```http
GET /api/v1/wallpapers?date=2026-08-31
GET /api/v1/wallpapers?from=2026-08-01&to=2026-08-31
```

Only one query mode is valid:

- Exact date: `date` is present and `from` and `to` are absent.
- Closed range: `from` and `to` are both present and `date` is absent.

All values use the same real `YYYY-MM-DD` calendar-date format as the Composer
command. A range includes both endpoints and requires `from <= to`. Version 1
has no product-level range limit and no pagination.

The endpoint returns matching records ordered by `sourceDate` descending and
then `id` descending. The secondary order makes results deterministic if future
sources produce more than one record for a date.

### Successful response

A valid request returns HTTP `200`, including when no records match:

```json
{
  "data": [],
  "meta": {
    "query": {
      "date": "2026-08-31",
      "from": null,
      "to": null
    },
    "count": 0
  }
}
```

`meta.query` always contains all three keys. Exact-date mode sets `from` and
`to` to null; range mode sets `date` to null. `count` is the number of elements
in `data`.

Each `data` element exposes only:

| Field | Type |
| --- | --- |
| `id` | non-empty opaque string |
| `source` | non-empty string |
| `market` | non-empty string |
| `sourceDate` | `YYYY-MM-DD` string |
| `title` | string or null |
| `copyright` | string or null |
| `copyrightLink` | absolute HTTPS URL or null |
| `imageUrl` | absolute HTTPS URL |
| `downloadUrl` | absolute HTTPS URL or null |

The public representation never includes `sourceItemId`, `rawPayload`, sync
records, process output, stack traces, database details, or internal errors.

### Validation response

Missing, mixed, incomplete, invalid, or reversed query modes return HTTP `422`:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request parameters are invalid.",
    "details": [
      {
        "field": "date",
        "code": "INVALID_DATE",
        "message": "The date must be a real calendar date in YYYY-MM-DD format."
      }
    ]
  }
}
```

`details` is a non-empty array ordered by `date`, `from`, `to`, then `query`.
Each detail contains exactly `field`, `code`, and `message`. The stable v1 detail
codes are:

| Condition | Field | Detail code |
| --- | --- | --- |
| Neither query mode supplied | `query` | `QUERY_MODE_REQUIRED` |
| Exact and range parameters mixed | `query` | `QUERY_MODE_CONFLICT` |
| `from` supplied without `to` | `to` | `RANGE_ENDPOINT_REQUIRED` |
| `to` supplied without `from` | `from` | `RANGE_ENDPOINT_REQUIRED` |
| A supplied date is not canonical and real | its parameter name | `INVALID_DATE` |
| Valid endpoints have `from > to` | `query` | `RANGE_ORDER_INVALID` |

Mode errors take precedence over date-format and range-order errors. Format
errors take precedence over range order. Clients must use codes for behavior and
may display the English messages as a fallback.

## Contract fixtures

Reusable examples live under `tests/Fixtures/Contracts`:

- `composer/` covers `found`, `not_found`, `error`, a compatible optional-field
  addition, and an unsupported major version.
- `api/` covers exact-date and range success, an empty result, and validation.

Fixtures are contract examples, not captured production payloads. They contain
no credentials, user information, or live service dependency.
