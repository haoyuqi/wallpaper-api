# Wallpaper service deployment

This Compose project runs the [wallpaper-web](https://github.com/haoyuqi/wallpaper-web) frontend, the wallpaper API, and exactly one scheduler. The frontend serves `/api` from the API over the private Compose network; only the frontend port is published. The authentication service is deployed separately. This deployment does not download or store image binaries.

1. Copy `.env.example` to `.env` in this directory. Set `APP_KEY` and `DB_PASSWORD`. The `WEB_VERSION` and `API_VERSION` settings default to `latest`; set each to a published `vX.Y.Z` tag for predictable upgrades. Generate a key with `openssl rand -base64 32`, prefix it with `base64:`, and keep `.env` private. For external PostgreSQL set `DB_HOST` to its reachable hostname; for the bundled database leave `DB_HOST=postgres`.
2. Start the database if bundled: `docker compose --profile bundled-db up -d postgres`. For an external database, arrange the database and credentials outside Compose.
3. From this directory, run `docker compose run --rm --no-deps api php artisan migrate --force`. Migration is explicit and should be performed once per release before bringing up the application; never run a destructive rollback on production.
4. Start the services: `docker compose up -d` for an external database, or `docker compose --profile bundled-db up -d` for the bundled database. Check `docker compose ps` and `curl --fail http://localhost:8080/healthz` for the frontend. Check the API from within its container with `docker compose exec api php -r 'exit(@file_get_contents("http://127.0.0.1:8080/up") === false ? 1 : 0);'`. Public queries are available under `/api/v1/wallpapers`.

The scheduler uses the same API image and calls Laravel `schedule:work`; it executes the existing daily UTC schedule. Its file-cache overlap lock lives in the persistent `scheduler_cache` volume. Keep only one Compose scheduler instance. PostgreSQL data lives in `postgres_data` when bundled. `docker compose down` preserves both volumes; `down --volumes` deletes their data and must not be used for routine shutdowns. Back up the database before schema changes and arrange TLS, firewall, monitoring and a public reverse proxy separately.

The frontend `/healthz` checks Nginx; the API `/up` checks that Laravel boots. Neither proves PostgreSQL availability or yesterday's sync succeeded. Inspect `docker compose logs scheduler` and synchronization audit records for freshness. Pin and upgrade both image versions deliberately, then rerun the migration step; existing images and the same `APP_KEY` enable rollback when the schema remains compatible. The API's CI smoke checks both architectures with disposable PostgreSQL and validates Compose with external and bundled database modes; once both published images exist, verify the combined stack before production use. GHCR package visibility and access must be configured for the intended audience before pulling images from another host.
